## Goal

A Flappy Bird game rendered with the real-time 3D layer, using the asset set generated by
`tools/blender/generate_flappy_assets.py`. One endless run, tap to flap, score is pipes passed,
best score persisted. Portrait, touch-first, same chunky flat-colour art direction as Sokoban.

## Scope

In: the endless run, its HUD, its 3D world, the shared host extraction it needs, a menu entry,
high-score persistence, unit tests for the simulation.

Out: challenge levels, level-select integration, medals/achievements, sound, a 2D fallback
renderer, leaderboards.

## Architecture

Three layers, each with one job, and a hard rule that the middle one knows about neither engine.

```
FlappyGameScene   (Phaser)  input, HUD, restart, frame loop, persistence
      |  steps                       ^
      v                              |  reads state
FlappySim         (pure TS)  gravity, pipes, scoring, collision, phase machine
      |  state
      v
FlappyWorld       (three)   bird, pipe pool, tiling ground, parallax props, camera
      |  hosted by
      v
ThreeHost         (three)   canvas, renderer, viewport, model cache, frame dispatch
```

`FlappySim` imports nothing from Phaser, three.js or the DOM. That is what makes it testable
(ADR 0004) and what keeps the game's feel — the part that needs tuning — in one readable file.

### ThreeHost and world modules

Extracted from `ThreeSokobanLayer` per ADR 0002. The host keeps: canvas creation and mounting,
lazy renderer creation after Phaser has claimed the first WebGL context, `bindGame`, viewport
sync against Phaser's canvas rect, the play-area view offset, the glTF loader with its model and
clip caches, `show`/`hide`, and `render(dt)` which delegates to the active world and then draws.

```ts
export interface ModelSpec {
  key: string;
  url: string;
}

export interface ThreeWorld {
  readonly models: ModelSpec[];
  build(): boolean;
  frame(deltaSeconds: number): void;
  camera(): THREE.Camera;
  viewportChanged(width: number, height: number): void;
  clear(): void;
}
```

`ThreeHost.setWorld(world)` clears the previous world first. `SokobanWorld` is today's code
behind this interface with no behavioural change, keeping `boardQuarterTurns`,
`gridAtViewportFraction`, `topMarginFraction` and the follow camera. `FlappyWorld` is new.

### FlappyWorld

Owns the visual side only — it is told where things are, it never decides.

```ts
build(): boolean
setBirdPose(y: number, pitchRadians: number): void
setPipes(pipes: ReadonlyArray<{ id: number; x: number; gapBottom: number }>): void
setScroll(distance: number): void          // wraps ground segments and parallax props
playBirdClip(name: 'flap' | 'glide' | 'fall'): void
```

- Bird at world x = 0 always; the world scrolls past it. Placement and pitch go on `Bird_Root`,
  which is inert by design — see [issues/animated-root-node-discards-placement](../issues/animated-root-node-discards-placement.md).
- Pipes are a pool of 5 pairs, assigned by index from `setPipes`. Ceiling pipes are rotated π
  about X and placed at `gapTop + PIPE_LENGTH`; floor pipes sit at `gapBottom - PIPE_LENGTH`.
  Unused pool slots are moved off-screen rather than added and removed each pass.
- Ground is 4 segments of `ground.glb`, wrapped by `setScroll` with the 0.02 overlap the asset
  wants, and drawn shifted down by its 0.51 thickness so the surface lands on y = 0.
- Clouds and bushes wrap at their own fractions of the scroll distance for parallax.
- Camera: orthographic, fixed, `VIEW_WIDTH` wide, centred at `viewHeight / 2` so the ground line
  sits on the bottom edge. A small tilt (8° elevation, 10° azimuth) shows the pipes' round sides
  and the ground's top face. Orthographic on purpose: with no perspective the mapping from
  simulation units to screen is exact, so a collision that looks unfair is a tuning problem
  rather than a projection artefact.

### FlappySim

State, tuning and behaviour in one file. `step` mutates and returns the same object — a run
allocates nothing per frame.

```ts
export type FlappyPhase = 'READY' | 'FLYING' | 'DYING' | 'GAME_OVER';
export interface FlappyPipe {
  id: number;
  x: number;
  gapBottom: number;
  scored: boolean;
}
export interface FlappyState {
  phase: FlappyPhase;
  birdY: number; // world units, ground surface = 0
  velocity: number; // units/second, positive is up
  pitch: number; // radians, derived from velocity
  scroll: number; // total distance travelled, for ground/parallax wrapping
  pipes: FlappyPipe[];
  score: number;
  nextPipeId: number;
}
```

- `createFlappyState(config)` — `READY`, bird at `startY`, no pipes.
- `flap(state)` — `READY` starts the run and applies the impulse; `FLYING` applies it; `DYING`
  and `GAME_OVER` ignore it.
- `step(state, dtSeconds, config)` — integrate, scroll, spawn/recycle pipes, score, collide.
- `random: () => number` comes from the config so pipe placement is deterministic in tests.

Phases: `READY` (bird hovers, no gravity, no pipes) → `FLYING` → `DYING` (collision happened;
gravity only, input ignored, `fall` clip) → `GAME_OVER` (bird has reached the ground).

### Tuning, and where the numbers come from

Derived from the original game's proportions rather than guessed, anchored on our pipe being
1.1 units wide where the original's is 52 px: **1 original pixel = 0.02115 units**.

| Constant           | Value              | Derivation                                             |
| ------------------ | ------------------ | ------------------------------------------------------ |
| `VIEW_WIDTH`       | 6.1                | 288 px screen width                                    |
| `pipeGap`          | 2.6 (derived 2.0)  | 100 px gap, but playtested up — see below              |
| `pipeSpacing`      | 3.0 (derived 2.35) | 110 px between pipe centres, playtested up — see below |
| `scrollSpeed`      | 2.54 → 3.40        | 120 px/s, ramping +0.02 per point                      |
| `gravity`          | −21.0              | ~1000 px/s²                                            |
| `flapImpulse`      | 5.3 (derived 7.2)  | ~340 px/s, but playtested down — see below             |
| `terminalVelocity` | −11.0              | keeps a long fall readable                             |
| `startY`           | 3.5                | mid-air, clear of the first pipe                       |
| `gapMargin`        | 1.2                | keeps a gap off the floor and ceiling                  |
| `birdHalfWidth`    | 0.31               | forgiving: the mesh is 0.96 × 0.51                     |
| `birdHalfHeight`   | 0.20               | forgiving, as above                                    |
| `pipeHalfWidth`    | 0.55               | the rim's real radius                                  |

`viewHeight` is not a constant — it is `VIEW_WIDTH / aspect`, passed in by the scene, and the
gap range is `[gapMargin, viewHeight − pipeGap − gapMargin]`. On a portrait phone that is about
13.3 units tall.

**`flapImpulse` was overridden after playtesting.** The pixel-derived value (7.2) rises
`v0² / (2·|gravity|) = 1.23` units on a single flap — 62% of the whole `pipeGap` (2.0), not the
~1/3 a controllable flap should cost. In practice this made the game nearly unplayable: one tap
could already carry the bird most of the way through the gap's vertical room, leaving almost no
margin for a second tap to correct with, and even a scripted adaptive-tap test (reading the
bird's live height between taps) kept overshooting the gap. Retuned to 5.3, landing the rise at
`pipeGap / 3` (0.669 vs a target of 0.667). `gravity` and `terminalVelocity` were left at their
derived values — only the impulse needed to move.

**`pipeGap` and `pipeSpacing` were also widened after playtesting.** At the derived spacing
(2.35), the edge-to-edge air pocket between consecutive pipes
(`pipeSpacing − 2·pipeHalfWidth` = 1.25) was narrower than the pipe-plus-bird collision width
itself (`pipeHalfWidth + birdHalfWidth` = 0.86), leaving almost no slack unless the bird was
already dead-centre when the next pipe arrived. The vertical room
(`pipeGap / 2 − birdHalfHeight` = 0.8) felt cramped for the same reason even flying level.
Widened to 2.6 and 3.0 respectively: more reaction time between pipes, and more forgiveness
lining up each gap. `flapImpulse`'s rise is now `0.669 / 2.6 ≈ 26%` of the gap — comfortably
under the `⅓` target rather than sitting right at it.

A frame longer than 1/30 s is integrated as multiple sub-steps, so a stall cannot teleport the
bird through a pipe.

Hitting the ceiling clamps velocity to 0 rather than killing, as in the original. The floor
kills: `birdY − birdHalfHeight <= 0`.

### Asset change required

`pipe.glb` must be regenerated at `PIPE_LENGTH = 10.0` (currently 4.0). At 4 units a ceiling
pipe placed against a gap high in a 13-unit-tall view leaves a visible hole above it. Pipe
length has no gameplay meaning — only the rim's position does — so the fix is a longer column,
which costs no triangles because a cylinder's segment count is independent of its length.

### FlappyGameScene

- Input: `pointerdown` anywhere outside the HUD, plus `SPACE` / `UP`. One tap is one flap.
- Frame: `update(_, delta)` steps the sim, pushes the result into `FlappyWorld`, renders through
  `ThreeHost`, updates the score text.
- Clips: `flap` on each tap, `glide` while coasting, `fall` on entering `DYING`.
- HUD: score top-centre; "Tap to fly" on `READY`; on `GAME_OVER` a card with score, best, a
  "new best" flag, Retry and Menu. Built with the existing `createButton` / `uiFont` / `PLAY_AREA`.
- Persistence: `ProgressService.completeLevel(FLAPPY_LEVEL_ID, score)` once, on entering
  `GAME_OVER`; `getHighScore(FLAPPY_LEVEL_ID)` for the best shown.
- Restart resets the sim and world without re-entering the scene, so retry is instant.

### No-WebGL behaviour

There is no 2D flappy art and none will be invented for this. When `ThreeHost.isReady` is false,
`MenuScene` does not show the Flappy button, and entering the scene directly shows a short
"3D not available on this device" message with a Menu button. Sokoban keeps its own 2D fallback;
this game simply is not offered.

## Verification

The simulation has unit tests. Everything else is verified by running it, and the plan states
the checks per phase. Two are non-negotiable:

1. **Sokoban must not regress.** After the host extraction and before any Flappy code: level
   #101 loads in 3D, tap-to-move walks a route, and the follow camera tracks the player on a
   quarter-turned board (`camTarget.z` changes as the player moves — the exact check from `docs/issues/rotated-board-grid-vs-world-coordinates.md`).
2. **The bird must be visibly killable and scoreable.** A run reaches score ≥ 1, a crash into a
   pipe and a crash into the ground both reach `GAME_OVER`, and the best score survives a reload.

## Risks

- **The extraction is the risky part, not the game.** It touches the most fragile code in the
  repo (WebGL context ordering) for a feature that does not need Sokoban at all. Mitigation is
  ordering: extract first, verify Sokoban, commit, and only then start Flappy.
- **Tuning is a feel problem.** The table above is derived, not playtested. Expect one pass of
  adjusting `gravity`, `flapImpulse` and `pipeSpacing` after playing it; they are deliberately
  all in one exported object so that pass is a single-file change.
- **Portrait aspect drives `viewHeight`,** so an unusual window shape changes how much vertical
  room the gaps get. The gap range is computed from `viewHeight` rather than hardcoded for this
  reason, but a very short landscape window will feel cramped. Portrait is locked in
  `main.ts`, so this affects desktop browsers only.
